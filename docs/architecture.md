# FrigoTab architecture and test boundaries

FrigoTab is a small native Win32 application written in Rust around Win32 window enumeration, DWM thumbnails, and the Explorer desktop surface. The application has one UI message loop. The low-level keyboard hook does only bounded event handling and posts session work to that loop; enumeration, window construction, painting, and native preview setup do not run inside the hook callback.

The application creates one preview window per selectable candidate. The backdrop is not composed from those application windows.

The package folders group related modules, and each named production struct or enum has its own source file. `src/lib.rs` re-exports the former flat module paths for compatibility; those aliases refer to the same types and contain no duplicate implementations. New code uses the package paths directly.

The owner HWND stores one stable context. Mutable application state is protected by checked `RefCell` borrows, while its cloneable `SessionPainter` owns only the independently shared backdrop state. This matters because Win32 may synchronously deliver `WM_PAINT` from inside another native call: the callback can repaint the real first frame without creating a second mutable reference to the application or session.

## Session and input flow

1. The hook gates a non-injected Alt-down until the next key identifies a switcher chord. Alt-first Alt+Tab transitions are consumed as one gesture, and other physical keys remain quarantined while that gesture is pending or visible; ordinary Alt-only and Alt+key input is replayed as a balanced native chord. If Sticky selection activates or closes the session while Alt is still held, a later distinct Tab starts a fresh admission while the original Alt release remains suppressed. Ctrl+Alt bypasses the gate so AltGr and Ctrl+Alt+Tab stay native. The bounded switcher event is posted to the UI loop.
2. The controller asks the session view to enumerate eligible windows and build the overlay.
3. The view lays out real candidate HWNDs and configures their DWM thumbnails while the owner remains hidden, allowing the compositor to prepare the redirected source surfaces off-screen.
4. The view shows and synchronously paints the owner from the selected backdrop (the retained shell snapshot in Full desktop mode), then shows the already-rendered title/number overlays. Tab/Shift+Tab, numbers, and pointer movement update the selected candidate.
5. The tray-selected close-button mode controls each tile's affordance. `Always visible` (the default) paints a 32x32 black button with a white `×`; `On hover (Alt-Tab / Win-Tab)` paints only a white `×` without a background on the tile currently under the pointer, independently of keyboard selection; `Hidden` paints no close affordance. A pointer hit on a visible close affordance asynchronously posts `WM_CLOSE` to the exact source HWND, clears selection, and leaves a Sticky session open. While the session is visible, a lightweight timer checks its existing source HWNDs; when a source closes either through FrigoTab or independently, the candidate list is rebuilt and the live thumbnails are reflowed and renumbered while retaining the session and foreground overlay. In Hidden mode, the same region is handled as ordinary tile activation.
6. In the default Sticky mode, releasing Alt does not commit the first candidate; the session remains available until an explicit number/pointer activation or Escape/Alt+F4 cancellation. Tray-selected Tap (classic) commits the current selection on Alt release.
7. Activation restores a minimized target and attempts `SetForegroundWindow` after the historical zero-key input nudge. The nudge carries an internal marker and FrigoTab's hook consumes its exact shape before it can become a keyboard message in either the previous or selected application. The controller then closes and disposes the session.

The handoff intentionally does not use `AttachThreadInput`; joining input queues can corrupt focus and key-state isolation. Windows may still deny foreground activation, in which case the overlay remains usable.

## Shell desktop snapshot

In the default `FullDesktop` mode, `ShellDesktopSnapshot` locates Explorer's desktop host (`Progman`, or the `WorkerW` containing `SHELLDLL_DefView`/`SysListView32`) and calls `PrintWindow` with `PW_RENDERFULLCONTENT` into an off-screen compatible bitmap. The resulting top-down DIB is retained while the application is idle and reused when a session opens. This avoids a screen capture and avoids searching/filtering/composing the background from application windows. `ImageOnly` calls `PaintDesktop` directly into the owner DC, so it paints the desktop pattern or wallpaper without desktop icons. `Black` fills the owner with `PatBlt(BLACKNESS)` and does not touch Explorer.

If the shell host or render is unavailable in `FullDesktop` mode, the most recent matching frame is used when possible; otherwise the owner paints black. The image-only and black modes do not require a shell snapshot. Partially created HDCs, HBITMAPs, and native wrappers are released on every failure path. A display/DPI topology change can close the current session and request a correctly sized replacement.

## DWM and resource lifetime

Each preview registers a DWM thumbnail against the hidden owner. Its destination, opacity, and visibility are set together so DWM can prepare the live source before the owner is exposed; owner visibility still prevents a partial session from appearing. Teardown hides the owner and unregisters each thumbnail with its native resources. When DWM is unavailable, the tile retains its icon/title fallback.

Windows, icons, fonts, layered DCs, bitmaps, thumbnails, hook handles, the tray icon, and the single-instance guard have explicit ownership and are disposed during normal close, failed construction, tray Exit, and process shutdown.

## Acceptance boundary

The automated gate has 62 tests in fifteen timestamped plain Rust integration-test modules. The tests use real HWNDs and native Windows resources, including DWM/GDI, the Explorer shell surface, owner-linked application/tool windows, the real tray popup, exact fixture `KeyboardMessage` logs, and the launched executable. Session behavior is observed through an external process and the production `WH_KEYBOARD_LL` hook; non-keyboard low-level cases use real Win32/DWM objects. There is no `LiveSession`, controller-fed acceptance harness, `WM_BEGIN_SESSION` path, fake session, or BDD layer. The tests verify observable behavior such as rapid balanced Tab release, Sticky and Tap release, held-Alt reopening after activation, marked real-hook delivery, ordered replay, Alt-first and Shift-first suppression, native Ctrl+Alt handling, visible-session quarantine, navigation, selection, tray-only runtime settings, owned tool-window grouping, the three close-button modes and exact-source close requests, live refresh/reflow/renumbering after both requested and independent source closure, all backdrop modes, stale-window recovery, first-frame backdrop ordering, first-frame thumbnail readiness, DWM visibility, process lifetime, visual parity, and cleanup. Every process scenario waits for the owner-window ready barrier before sending input and clears fixture logs after startup foreground changes.

Normal production launches ignore injected and lower-integrity injected events by design. The explicit `--accept-marked-test-input` acceptance launch admits only tagged `SendInput` events, while FrigoTab's own unmarked replay remains ignored; this exercises the real hook ledger without changing normal behavior. Windows marks these events with `LLKHF_INJECTED`, so the marker is test-only provenance filtering, not a security boundary. Marked input differs from hardware in scheduler timing, batching, typematic/autorepeat, virtual-key/scan-code/extended flags, keyboard layout and AltGr behavior, and interaction with already-held physical modifiers. The bounded panic-safe modifier/consumed-key ledgers, explicit foregrounding, readiness barrier, and exact logs mitigate those effects but do not remove them. `VK_RMENU` through `SendInput` synthesizes Ctrl on layouts such as Hungarian, so plain Right-Alt+Tab remains a manual physical check rather than an automated claim.

PostMessage/SendMessage and UI Automation bypass global input routing and `WH_KEYBOARD_LL`, so they are less realistic for keyboard acceptance and are limited to deterministic setup. Virtual HID/VHF or a signed driver is closer to hardware but requires administrator access, WDK/kernel code, driver signing/install, and Windows-version policy maintenance. Physical USB HID or keyboard-robot input is highest fidelity but needs hardware and a manual lab. UIPI/elevation, lower-integrity injection, secure desktop/lock screens, RDP, exclusive fullscreen, raw-HID consumers, Explorer/DWM state, hook timeout/removal, and heavy-load behavior remain in the physical/special release matrix. The automated results are necessary evidence, not a claim that every Windows desktop configuration is identical.
